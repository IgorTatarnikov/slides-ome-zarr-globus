From files on disk to OME-Zarr

Converting light-sheet and BrainSaw volumes for neuroglancer, and sharing them over Globus

Igor Tatarnikov

2026-10-28

Whole-brain microscopy is big

Light-sheet

  • 2123 × 8879 × 6030 voxels, uint16
  • 5 × 2.71 × 2.71 µm
  • 227 GB per channel

Serial two-photon (BrainSaw)

  • 2660 × 6431 × 8662 voxels, uint16
  • 5 × 1.2 × 1.2 µm
  • 275 GB per channel

Why OME-Zarr?

  • Open format for large, multi-dimensional images
  • Chunked, and standardised
  • Compatible with cloud-based storage and parallel access
  • A pyramid of downsampled copies can be added making visualisation fast

Ideal world for converting a large file

  • Try to reach the point where you’re I/O bound (typically write-bound)
    • SATA SSD: ~0.4 GB/s
    • NVMe SSD: ~3 GB/s
    • Ceph: 🤷
  • Avoid reading the same data multiple times
  • Keep memory usage bounded
  • Compress before writing
  • Minimise the number of files

What OME-Zarr asks of you

scan.ome.zarr/
├── zarr.json        - OME metadata: axes, units, scale per level, channels
├── s0/              - full resolution, (c, z, y, x)
│   ├── zarr.json    - shape, chunk grid, codecs
│   └── c/0/0/0/0    - one shard file
├── s1/              - half size in each axis (Z only once voxels are near-isotropic)
│   ...
└── s7/              - about one chunk across

Targeting OME-Zarr 0.6, on Zarr v3 with sharding.

Start with the metadata, not the data

Write every zarr.json and no data, then inspect it:

image = ngff_zarr.to_ngff_image(lazy_array, dims=["c", "z", "y", "x"],
    scale={"z": 5.0, "y": 2.708, "x": 2.708},
    axes_units=dict.fromkeys("zyx", "micrometer"), channel_names=names)
ms = ngff_zarr.to_multiscales(image, scale_factors=factors, chunks=64)
ngff_zarr.to_ngff_zarr(out, ms, version="0.6",
    chunks_per_shard=512 // 64, metadata_only=True)
  • Cheap to iterate on: shapes, units and scales are all visible in seconds
  • Easy to round trip and verify the metadata reads back

Chunks are optimised for fetching data

  • 64x64x64 uint16 is 512 KiB per chunk
  • Small cubes respond at any slicing angle: xy, xz, yz and 3D all fetch the same units
  • Chunk size is set for the viewer

Shards are optimised for storage and transfer

  • Shards group many chunks into one file
  • Reads are chunk based, writes are shard based
layout files
one file per 64x64x64 chunk 514,930
512x512x512 shards of 64x64x64 chunks 1,283
  • Shard size is set for the filesystem (and for backups, Globus transfers, ls)

Compression

Measured on real 64x64x64 chunks from the light-sheet data:

codec ratio speed per core
zstd, level 6 1.68 128 MB/s
blosc(zstd, level 3, byte-shuffle) 1.80 887 MB/s
  • Byte-shuffle groups the high bytes of every uint16 together

Resolution pyramid

  • X and Y halve at every level
  • Z halves only once the XY spacing has caught up with it, so anisotropic stacks aren’t blurred in Z too early
voxel (x, y, z) level 1 level 2 level 3
2.71, 2.71, 5 µm 2, 2, 1 4, 4, 2 8, 8, 4
2.18, 2.18, 5 µm 2, 2, 1 4, 4, 2 8, 8, 4
  • Add levels until the top one is about one chunk across
  • For mouse brains that’s 8 levels, with a top level of 16 × 69 × 47

ngff-zarr as the writer

Hand the whole array to ngff-zarr and let it write:

ngff_zarr.to_ngff_zarr(out, ngff_zarr.to_multiscales(image, ...))
  • 0.10 GB/s, about 38 min for one 227 GB channel (local SSD)

Ok for small data, but I’m impatient!

Write in the right order

one shard-thick layer of s0, seen looking down Z:

      X ->
 +-------+-------+-------+-------+
 | shard | shard | shard | shard |   <- one band
 +-------+-------+-------+-------+
 |    next band, below in Y      |
 +-------+-------+-------+-------+
  • A band is all channels × one shard deep × one shard tall × the full width in X
  • Full-width rows are how most data is laid out on disk. Row reads ran at 380 MB/s against 34 MB/s for cube reads.

Build the pyramid on the way past

  • s1 is block-meaned from each band while it is still in memory
    • 2 to 4 s0 bands make one s1 band, which is also written once, whole
  • s2 onward is made from the level before it, one shard per task
    • That’s at most 1/8 of s0’s size, so it takes about a minute
  • s0 is never read back from the output

zarr-python vs tensorstore

On the cluster (Ceph), 2-channel OME-TIFF:

writer throughput
zarr-python 0.04–0.08 GB/s
tensorstore 0.36 GB/s

Reads depend on the storage

  • Ceph serves parallel reads much faster
    • On a 593 GB BrainSaw stack, reads ran at 1.56 GB/s
  • A local NTFS disk serialises I/O, so parallel reads were slower: 290 vs 400 MB/s

On Desktop

One 227 GB channel, read from and written to the same local NTFS SSD:

strategy time
naive ngff-zarr ~38 min
tensorstore ~22 min

Serving it

  • Neuroglancer reads single chunks out of shards with HTTP Range requests, and it needs CORS
  • A Globus guest collection with public read provides both

Neuroglancer quirks

  • The hosted demo ignores some metadata and opens nearly black
  • Axes are shown in file order (z, y, x), so the “xy” panel shows z against y
  • A full state in the URL is long and fragile

Ship a state file beside the store

scan.ngl.json sits next to scan.ome.zarr, and the link just points at it:

  • One additive layer per channel, with colour and contrast taken from omero
  • Axes ordered x, y, z, so “xy” really is xy
  • Starts zoomed out, with the 3D view optionally in the corner, the shader controls docked, and optional volume rendering
